# Commerce Frontend QA

## Purpose

Run one consistent merchant-facing UI audit and produce route/state-specific PASS/FAIL evidence.

## When To Use

- After changes to React components, styles, routing, translations, loading/error states, or API
  response contracts.
- Before release claims involving the merchant UI.

## When Not To Use

- Do not replace backend authorization tests or provider acceptance with browser appearance checks.
- Do not run only screenshots; assertions and browser/network error collection are mandatory.

## Inputs

- A disposable checkout running through `commerce-clean-bootstrap`.
- API on 8000, Vite on 5173, independent worker ready, and the one-time demo password.
- Chrome available at the path used by the committed Playwright scripts.

## Workflow

1. Run static frontend quality gates:

   ```powershell
   npm --prefix web run lint
   npm --prefix web run test
   npm --prefix web run build
   npm --prefix web run format:check
   ```

2. Run the core transactional journey first, then the broad route matrix:

   ```powershell
   $env:UI_DEMO_PASSWORD = Read-Host "One-time local demo password"
   npm --prefix web run verify:journeys
   npm --prefix web run verify:ui
   Remove-Item Env:UI_DEMO_PASSWORD
   ```

3. Require Arabic RTL and English LTR, public desktop/tablet/mobile breakpoints, authenticated
   merchant routes, theme/device states, COD lifecycle, named controls, image alternatives,
   no horizontal overflow, and empty browser error collections.
4. For loading, empty, error, permission-denied, and provider-disconnected states, use deterministic
   fixtures or existing test seams. Do not alter production records merely to manufacture a state.
5. Preserve only safe screenshots generated by the verifier; inspect them for clipping, overlap,
   stale language, broken hierarchy, and accidental sensitive data before sharing.

## Expected Output

- Frontend lint, tests, type-aware production build, and formatting pass.
- Login, home/command, Inbox, Content Studio, products, integrations, settings, and all committed
  routes render in their expected direction.
- Desktop and mobile layouts have no overflow or inaccessible unnamed controls.
- Console, page, failed-request, and unexpected HTTP-error collections are empty.

## Failure Conditions

- Any primary route, language direction, breakpoint, or required state is skipped.
- Visual success masks console errors, failed requests, 4xx/5xx responses, or inaccessible controls.
- Screenshots contain credentials, private customer content, or secrets.
- Local UI results are represented as deployed production acceptance.

## Verification

- Record candidate identity, exact commands, date, route count, breakpoints, directionality, state
  coverage, and error counts.
- Run `commerce-core-sales-e2e` and `commerce-content-e2e` for transactional interpretations.
